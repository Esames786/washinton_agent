# Data migration — Hello / CrazyRays

**Status:** plan. **Nothing has been copied, changed or deleted.**
**Written:** 13 October 2026, from read-only measurement of the live database.

---

## 1. Source and target

| | |
|---|---|
| **Source** | `hellotransport_databases` @ 199.250.220.27 — 257 tables, **255 MB** |
| **Target** | `crazyrayssolutio_crazzy` @ same server — **empty, 0 tables** |
| Target user | `crazyrayssolutio_crazzy2` |

Both are on the **same MariaDB 10.11.19 server**, which helps — but they sit under different cPanel
accounts, so **neither database user can see both databases**. Verified: the source user sees only
`hellotransport_databases`, the target user only `crazyrayssolutio_crazzy`.

**Consequence:** no server-side `INSERT … SELECT` across databases, and SSH is closed on this host.
The copy has to be driven by a client that holds both connections.

## 2. The number that shapes everything

The brand-specific data is **tiny**. Almost the entire 255 MB is shared reference data.

| | Rows |
|---|---|
| Brand-owned data — Hello | **7,793** |
| Brand-owned data — CrazyRays | **19,375** |
| Everything else (shared reference) | ~1.4 million |

So the migration is not a careful extraction. It is: **copy the whole database, then delete 7,793
Hello rows from the copy.**

## 3. Table classification — decided by measurement

Full list: [`TABLE-CLASSIFICATION.md`](TABLE-CLASSIFICATION.md).

| Class | Tables | Action |
|---|---|---|
| **A** — brand-owned | 113 | Copy, then delete the other brand's rows |

### Correction to the first draft

`01-SPLIT-ARCHITECTURE.md` said *"every user-keyed table splits cleanly with zero orphans"*. That was
based on eight hand-picked tables and **was too optimistic**. Two things it missed:

**(a) `employee_id` does not point at `user`.** It points at `hr_employees.id`, which then resolves
through `hr_employees.agent_id`. Joined correctly, all **20** HR tables resolve **100%** — but a
migration written against the wrong join would have deleted almost all HR data.

**(b) Some tables carry a `user_id` from a different system.** They look brand-owned and are not:

| Table | Rows | Resolves to a local user |
|---|---|---|
| `shipper_details_fetch` | 681,809 | **0%** |
| `used_new_car_dealers` | 617,379 | **0%** |
| `shipper_details_fetch_edge` | 69,097 | **0%** |
| `carriers_archive` | 38,725 | 4% |
| `shipper_details_carriers` | 23,073 | **0%** |
| `general_settings`, `email_template`, `wp_priceperm`, `authorization_form` | small | 0% |

Those IDs belong to the **Washington CRM**, not this portal. Partitioning them on `is_crazyrays`
would have thrown away ~1.4 million rows. They are now Class B — copied whole to both sides.

**The classification must be generated by measurement at migration time, not read from this
document.** The rule used: a table is Class A only if **≥50%** of its rows resolve to a local user.

## 5. Method

A migration script holding both PDO connections, run from a controlled machine. Resumable, with a
verification pass. **Append-only into an empty target — the source is never written to.**

### Phase 1 — Schema (minutes)
For each of the 257 tables: `SHOW CREATE TABLE` on the source, execute on the target. No data.
*Check:* target table count = 257, and every column/index matches.

### Phase 2 — Data (≈255 MB)
Copy every table in batches of 1,000 rows, source → target, in primary-key order so it can resume.
*Check:* row count per table matches the source exactly, table by table.

### Phase 3 — Prune to CrazyRays
On the **target only**, for each Class A table:

```sql
DELETE FROM <table>
WHERE <user key> IN (SELECT id FROM user WHERE is_crazyrays = 0);
```

HR tables resolve through their employee:

```sql
DELETE FROM <hr table>
WHERE employee_id IN (
  SELECT h.id FROM hr_employees h
  JOIN user u ON u.id = h.agent_id
  WHERE u.is_crazyrays = 0);
```

Then `DELETE FROM user WHERE is_crazyrays = 0;` **last** — the queries above depend on it.

*Expected result:* 7,793 Hello rows removed; 19,375 CrazyRays rows remain. Class B untouched.

### Phase 4 — Verify
- Target Class A row counts equal the pre-measured CrazyRays figures
- Target contains **zero** users with `is_crazyrays = 0`
- Class B counts identical on both sides
- Spot-check: a known CrazyRays agent still has their orders, HR record, attendance and documents

### Phase 5 — Hello side
Hello keeps the **existing** database. Only after CrazyRays is verified and live does Hello prune
its own CrazyRays rows — so there is always one intact copy of everything.

## 6. Order of operations

1. Answer §4 (the 182 rows) and the three blocking questions in `03-START-HERE.md`
2. **Take a full backup of the source.** cPanel → Backup, download it, verify it opens
3. Phases 1–2 — the target is populated but nothing is live
4. Phase 3–4 — prune and verify, still nothing live
5. Point `florida.crazyrayssolutions.com.pk` at the new database, new bridge keys
6. Run CrazyRays live on the new database for one week, Hello untouched on the old one
7. Only then, Phase 5

**At no point before step 7 is a single row deleted from the live database.** If anything is wrong,
CrazyRays is pointed back at the old database and nothing is lost.

---

## 7. Risks

| Risk | Mitigation |
|---|---|
| A table mis-classified, data wrongly deleted | Classification generated by measurement at run time; Phase 3 runs only on the copy |
| Auto-increment collisions later | Both sides keep the original IDs; they diverge only after cutover |
| Foreign keys / triggers | Check for them in Phase 1 — MariaDB will reject out-of-order deletes if FKs exist |
| Long copy, source still changing | Run Phase 2 at a quiet hour; re-sync Class A tables (27k rows, seconds) immediately before cutover |
| Hello pruned too early | Phase 5 is deliberately last, after a week of CrazyRays running clean |
